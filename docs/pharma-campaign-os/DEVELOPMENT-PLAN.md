# Pharma Campaign OS｜完整纵切 MVP 开发计划

**版本：** v0.1｜计划候选（未执行）  
**前置：** [PRD](./PRD.md) / [ENGINEERING](./ENGINEERING.md) / [RESEARCH](./RESEARCH.md) / [SOURCE-MAP](./SOURCE-MAP.md)

## 0. 本轮约束

本计划仅规划医药营销战役子项目，不改变 `AWKN-Lab/marketing` 原有 P0–P5 基线和在途 P6 #2 联调目标。文档入库独立 PR；后续每个大组件固定一条工程分支/一个 PR，禁止同组件重复开分支。执行前必须读取 GitHub current main、活跃 PR、源代码与本地运行真值，锁定 Exact SHA。

## 1. 产品验收主场景

品牌经理以一条有来源的专业教育机会信号发起战役 → 证据检索与 Claim 入库 → 同一 Brief 生成三种差异策略 → 五位反方逐一评审并留下 15 条记录 → Owner 查看风险、选案并冻结计划 → 生成两种材料 → 逐层 MLR 人工审批（展示一次驳回与重提交）→ 经许可的内部测试渠道或沙盒投放 → 收集真实技术回执或模拟回执 → 分析 KPI 和下一轮建议。

## 3. 单组件 PR 边界

- 文档 PR：`docs/pharma-campaign-os/*` + 文档索引；只涉及规划与源材料。
- 工程实现按 C01–C06 六个大组件独立 PR，每条分支沿用同组件唯一分支，不允许同时开启多条同组件线。
- Agent OS、Memory OS、MCP、UI、Forge 均为供体，不得在本项目 PR 中未经授权更改对方事实源。
- C01 的数据合同需优先冻结，C02/C03 可在合同确定后并行，C04/C05 必须共享 Claim/Approval 的验证规则，C06 读取只读事件。
- 推送、合并、部署遵守仓库实际许可与 Owner 治理；工程执行者不得自审放行。

## 4. 首轮研发任务

1. Fresh-read `marketing` 的 19 个 ProductOperation、TaskExecution、Material/Feedback/Outcome/Evolution 状态和 P6 在途改动，形成实际复用 mapping。
2. 将一场战役拆成 20 项合同验收用例，建立验收样本与数据分类。
3. 冻结 `Campaign`、`StrategySet`、`CritiqueRecord`、`AssetVersion`、`Approval`、`DispatchReceipt`、`OutcomeEvent` 的主键和事件字段。
4. 使用授权的公开资料/虚构样本跑通沙盒纵切，记录每个阶段耗时，区分人工待办与系统运行时间。
5. 以真实回执判断接入成熟度；仅当安全与执行硬门通过后，提出企业试点。

## 5. MVP 必须通过的负例

- 证据缺失或过期 → 内容不得批准；
- Claim 被撤回 → 依赖素材审批失效；
- 修改批准后素材字节 → 阻断发送并触发新审批；
- 反方评审与医学法务监管审批角色相混 → 权限拒绝；
- 无渠道授权/受众许可 → 阻断，记录原因；
- 同一发送重复触发、连接器超时重试 → 无重复触达；
- 无法获得提供方回执 → 保持 UNKNOWN/PENDING，禁止记 SUCCESS；
- 多租户交叉数据 → 零泄漏；
- 复盘无来源/模拟数据 → 不得计算真实 ROI。

## 6. 交付和停止条件

每项 PR 必须留下精确源码 SHA、测试命令/退出码、失败用例、浏览器流程、回退方案与审核责任人。本子项目目前仅有文档基线，无医药企业授权、无真实投放、无实测周期改善。任何强行跳过 MLR 审批或将模拟提升为真实结果的路径均必须停工并标记 BLOCKED。

**估算：** 隔离纵切的 10–14 天仅作排期参考，取决于现有代码质量与可用授权；不得承诺药企渠道几小时完成外部审批。
